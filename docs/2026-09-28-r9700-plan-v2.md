## The fp8 question

The AMD figure is real, but the full peak is out of reach here. Measured on this
card (`results/p0/wmma_peak-*.txt`):

| operand | register-resident coopmat peak | LDS-fed GEMM, 17408×512×5120 |
|---|---:|---:|
| f16 → f32 | 184 TFLOPS | 101 TF (our Q6_K kernel: ~86) |
| s8 → s32 | 356 TOPS | 169 TOPS |
| fp8 e4m3 → f32 (`VK_EXT_shader_float8`) | 371 TFLOPS | **not measured** |

AMD's larger "sparse" numbers need 2:4 structured sparsity, which RADV does not
expose. The number that limits a real GEMM is the **LDS-fed** rate, which is
~55% of the register peak on this driver. The ~2× over f16 is available only to
an 8-bit operand path. Two constraints decide which 8-bit type:

- **s8 is exact for weights**: Q6_K values are 6-bit integers. The cost is Q6_K's
  per-16 sub-block scale, and last round's int8 kernel lost to it (61 TF).
- **fp8 e4m3 is lossy for weights**: it represents integers exactly only up to
  16, and Q6_K spans −32..31. It would need the numerics gate and would likely
  fail it. It is plausible for **activations** and for the FA softmax/PV side,
  where the values are already rounded.

## Decode: where the 176k step goes and what is left

Step ≈ 73 ms for ≈ 3.4 tokens (46.8 t/s at acceptance ~0.80 on the depth prompt).
The composition below mixes measurements from different runs; D0 re-measures it
in one run.

| term | now | floor (fixed formats) | source |
|---|---:|---:|---|
| verify GEMV (all weights once, n=4) | 37.6 ms | 35.7 (22.9 GB @ 640 GB/s) | R6 perf logger |
| verify FA, 16 layers | 10.4 | 9.5 (6.1 GB of q8_0 KV) | R6 |
| verify other ops (~1,300 dispatches) | 6.0 | ~2 | R6 |
| 3 draft passes (MTP layer + 248k-row lm_head each) | ~9–11 | ~4 with a small draft vocab | 2026-09-25 profile, estimate |
| host / launch gaps | ~8 | ~1–2 | R5 (−2.1 already taken) |

The verify graph is at ~90% of DRAM already. The headroom is in everything
around it: drafts, host gaps, small ops (~15–20 ms of a 73 ms step), and in
**more accepted tokens per verify**. Verify cost is weight-bandwidth-bound, so
checking 6–8 candidates costs little more DRAM than checking 4.

The fixed-format decode ceiling at 176k is ~50 ms per step: verify 45 plus drafts
~4 plus host ~1. That is ~68 t/s at today's tokens per step, and more only by
accepting more tokens per verify. Every target is **re-derived after D0 and P0**
from their measurements, before the dependent task starts.

## Gates (in addition to the v1 Gates)

- **Draft-only changes** (D1, D2, D5 drafting side) cannot change what the verify
  pass accepts under greedy decoding. Gate: identical output text on the greedy
  identity check (both prompts), plus pooled acceptance on the 15-prompt set within
  −0.005. Verify-side numerics are untouched, so KLD is not required.
- **Any 8-bit arithmetic** (P1, P2) must pass both numerics gates: PPL ΔPPL ≤ 0.2%
  and decode KLD. Prefill FA also needs the MTP acceptance gate.
- **VRAM:** peak is 32,581 of 32,624 MiB while serving. Any new resident buffer
  must be paid for (smaller compute buffer, reuse), and must be measured at peak
  during a 176k prefill.
- End-to-end t/s A/Bs run **only in the main session**, in one quiet window
  (loadavg < 2), back to back, with the decode builds run twice.

## Decode tasks (first)

**D0 — one-run step budget.** Per-graph GPU time (verify, each draft) plus host gaps
at 70k and 176k in one server run: perf logger for GPU, and R5's
`GGML_VK_STEP_TIMING` / `LLAMA_DECODE_TIMING` for host. Output: the table above
with measured numbers for this build. Main session.

**D1 — cheap drafts: reduced-vocabulary draft head.** The MTP draft pass reads the
full 248,320-row lm_head (~1 GB, ~1.6 ms) three times per step. Drafts only need
top-1 candidates from a vocabulary subset. Build a draft-only output head over
the V most frequent tokens: V = 32k/64k, chosen from corpus token frequency and
stored as a row gather of the existing lm_head (same values, no new weights).
Tokens outside the subset are never drafted. Interface: `--spec-draft-vocab N`
(0 = full). Acceptance: identity gate, pooled acceptance within −0.005, draft
pass GPU time −1.2 ms or more per draft. Kill: acceptance loss > 0.01 at
the best V.

**D2 — GPU-resident draft chain on top of D1.** R7 built it (`r9700-r5-decodehost`
@ `2fc6d40aa`, opt-in `LLAMA_MTP_GPU_CHAIN=1`). It lost only because `token_embd`
lives in host memory. With D1, the chain needs embeddings only for the V draft
tokens: 64k × 5120 at Q6_K ≈ 270 MB, 32k ≈ 135 MB. That has to fit (see the
VRAM gate). Acceptance: identity gate; host time per draft phase ≤ 3 ms
(from ~11); decode 176k +≥ 4%.

**D3 — verify-side host time.** The remaining ~5–6 ms of host work per step
outside drafts: record the next graph while the GPU runs the current one,
reuse the graph across verify steps (inputs only change), and move sampling
bookkeeping off the critical path. Keep host-only changes bit-identical.
Acceptance: host ms per step (R5 timers) −3 ms; identity gate.

**D4 — verify small ops (~6 ms, ~1,300 dispatches).** From R6:
- GDN state gather plus CPY (1.2 ms): let gated_delta_net write snapshots straight
  into the cache.
- The 5120-wide RMS_NORM_MUL (0.78 ms): 4 workgroups at n=4, so split the rows.
- RMS_NORM→SCALE fusion activated via `keep_pattern`, keeping SILU_MUL fused.
- Dispatch count: fuse elementwise chains in the GDN block.

Acceptance: other-ops ≤ 3 ms per verify step; test-backend-ops for each touched op;
decode KLD.

**D5 — more tokens per verify (stretch).** First re-sweep n_max 3–6 once D1/D2 make
drafts cheap: the 2026-09-26 n_max=4 kill was priced with expensive drafts. Then a
feasibility spike for **tree verification** (top-k branches from each MTP draft
step, one verify batch with a tree mask). The hard part is the hybrid model:
gated-delta-net recurrent state must fork per branch. The verify path already
keeps 4 state snapshots, so measure the extra state memory and copy cost per
branch before building. Acceptance: tokens per step +≥ 10% at unchanged
verify-graph time; identity gate for n_max changes.

## Prefill tasks (after decode)

**P0 — 8-bit ceiling microbenchmarks (in `harness/wmma_peak/`, no llama.cpp).**
LDS-fed GEMM at 17408×512×5120 and 5120×512×17408 for:
- (a) fp8 e4m3 operands;
- (b) s8 with a **Q6_K-shaped epilogue**: int32 accumulate per 16-K, integer
  multiply by the 8-bit sub-scale, int32 accumulate across the 256-K super-block,
  one float convert per super-block;
- (c) f16 BK=64 as the no-precision-change reference.

Apply the two RDNA4 rules first: no conditional prefetch, and check LDS bank
mapping. Interface: `wmma_peak --gemm {fp8,s8q6,f16bk64}`. Go/no-go: P1 proceeds
with the path at ≥ 150 TOPS effective. Below that, P1 is re-scoped to f16 BK=64.

**P1 — 8-bit Q6_K GEMM.** Build the design P0 picked as a new module beside
`mul_mm_q6k_rdna4_f16`, keeping split-K, the n-fast order, and the swiglu fusion.
Activation quantization per token row per K-panel (for s8) or fp8 activations.
Acceptance: MUL_MAT and fusion tests; both numerics gates;
isolated ≥ 150 TOPS; pp2048 d0 ≥ 2,200. Kill: below 120 TOPS after two designs.

**P2 — prefill FA to ≥ 110 TF.** From R3's list:
- 64-byte V rows (recovers ~2 ms of 20.9 ms);
- s8 QKᵀ (K is q8_0, so exact; Q quantized per row, which needs the numerics
  gate), with PV kept in f16 because the V-scale trap still holds;
- or fp8 P×V if P0(a) shows fp8 LDS-fed throughput.

Acceptance: FA tests; both numerics gates; MTP gate; isolated ≥ 110 TF;
pp512 @ d131072 ≥ 1,000.

**P3 — prefill small ops at depth (~85 ms per 512-token ubatch at 131k).** Profile
with `prefill_profile.sh`, fuse the largest. Build chunked GDN prefill only if
it exceeds 5%.

**P4 — re-sweep** ubatch 512/1024/2048 and n_max with the final kernels; FINDINGS
entry.

## Order, bundling, execution

D0 → D1 → D2 (needs D1) ∥ D3 ∥ D4 → D5 → P0 → P1 ∥ P2 → P3 → P4.

| agent | tasks | why |
|---|---|---|
| main | D0, every end-to-end A/B, all merges and gate runs | measurements stay serialized and quiet |
| A | D1 + D2 | same draft path, builds on the R7 branch |
| B | D3 + D4 | the verify step's host and small-op overhead; different files from A (host code vs ggml-vulkan) |
| C | D5 | after A lands (needs cheap drafts) |
| D | P0 then P1 | the microbenchmark decides P1's design |
| E | P2 | independent shader |

Keep ≤ 3 agents at once (the GPU lock queue reached 4 deep and 40 minutes this
round). Each agent uses its own scratch-file prefix, does not run depth.sh, and
runs every GPU command under `gpu_lock.sh`.

## Constraints carried forward

- ACO: `x=0; if (ok) x=load` serializes the load. Use unconditional clamped loads.
- Compute the LDS bank mapping of every staging store before other tuning.
- The V q8_0 scale runs along head_dim, so int8 PV with a post-MMA scale is invalid.
- New variants go in separate shader modules with `GGML_VK_NO_<NAME>=1`.
- Judge acceptance pooled over ≥ 10 prompts. One greedy prompt swings ±0.04.
- Decode A/Bs only at loadavg < 2 to 4. Sibling CPU load cost 20% before.
- Q6_K MMVQ is a decode loss; the verify GEMV is at ~95% of DRAM. Leave it.
