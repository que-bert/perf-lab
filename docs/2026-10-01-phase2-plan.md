# Phase 2 plan: quants, multi-model, tuning, Qwen4 readiness (2026-10-01)

Phase 1 (Qwen3.8-27B Q6_K on the R9700) is closed: integrate16 serves, MPD2b was the last lever and missed
(+0.4%, rows MPD2b/MPD2b-AB). Phase 2 widens the target from one model/quant to the set below, and gets the fork
ready to bring up Qwen4-27B quickly when it ships. RDNA3 (7900 XTX) is out of scope.

## Targets

| model | arch | file / quant mix (bytes) | special features | status |
|---|---|---|---|---|
| Qwen3.8-27B | qwen35 (GDN hybrid, 1/4 attention, MTP 1) | Q6_K 92% (serving); Q4_K_M = Q4_K 67 / Q6_K 26 / Q5_K 6 | MTP drafting, 262k ctx, mmproj | serving, integrate16 |
| Ornith-1.5-9B | qwen35 (same as above) | Q4_K_M = Q4_K 67 / Q6_K 33; Q6_K | MTP 1 | loads in fork; not tuned |
| Qwen3.6-35B-A3B | qwen35moe (256 experts, 8 used, MTP 1) | UD-Q5_K_XL = Q5_K 54 / Q6_K 32 / Q8_0 13 | MoE (MUL_MAT_ID) | file present; not measured |
| Gemma4-E4B | gemma4 (42 layers, SWA 512 5:1, head dim 512 global / 256 SWA, per-layer embeddings) | `~/.lmstudio/.../gemma-4-E4B-it-Q4_K_M.gguf` = Q6_K 63 / Q4_K 36; 2.15 GiB is the per-layer embedding table (row lookups only) | no MTP, vision mmproj | not measured in fork (ollama blob does not load: FINDINGS 2026-09-11) |
| MiniCPM5-2B | llama | Q4_K_M = Q4_K 71 / Q6_K 29; Q8_0 | none | not tuned |
| Qwen4-27B | unknown until release | likely unsloth Q4/Q6 mixes | unknown | readiness work only (W9) |

What already transfers: attention/GDN/MTP-host work (qwen35, qwen35moe), fusions and host-overhead work (all),
Q6_K kernels (the Q6_K parts of every Q4_K_M file, and Gemma's output head), Q8_0 GEMM (MoE 13%).
What does not: Q4_K and Q5_K run upstream's generic kernels everywhere. They are 36-71% of every file
except the serving Q6_K.

## Decisions this plan takes, and open ones

- RB (`r9700-rb`, upstream merged, gates pass, texts 37/37, pooled -0.7%) becomes the phase-2 base after W1
  closes its gap. integrate16 keeps serving until then.
- **"Tuning" means two things here** (W6): kernel launch parameters per quant/shape on RDNA4, and runtime
  config per model (ubatch, KV types, draft settings, context).
- **Open: workload mix.** Interactive chat (decode-bound) vs long prompts/agent sessions (prefill-bound). It
  decides whether W8 (Q4/Q5 prefill GEMM, multi-day) runs. Until answered, decode work goes first.
- Qwen4 rumours are not planned against; W9 prepares for any successor arch.

## Workstreams, in order

### W0. Model-agnostic measurement harness (prerequisite, ~1 day, CPU + short GPU)
Every later item needs the same four numbers per model; today they are hard-wired to the 27B.
- `harness/model_profile.sh <model> <label> [bindir]`: decode t/s at 3 depths (short, 32k, model-max/2),
  prefill t/s at the same depths, and a `GGML_VK_PERF_LOGGER` op table for one decode step and one prefill
  ubatch. Writes one JSON per run under `setups/<setup>/results/`.
- `harness/model_quality.sh <model> <label> [bindir]`: PPL (`decode_kld.txt`, 8 chunks), decode KLD
  against a per-model reference made once from upstream at the model's own precision, and draft
  acceptance where the model drafts.
- Per-op bandwidth report: for each MUL_MAT/MUL_MAT_ID op in a decode step, achieved GB/s vs 640 GB/s,
  grouped by quant type.
- Setup folders: `setups/<model>-r9700/` per target (README with serving config, results/).
- Done when: all five present models have a profile and quality baseline from the same RB binary, and
  the same from plain upstream, all in one table.

### W1. Close RB's gap and make it the base (~0.5 day)
- Per-step host profile, i16 vs rb, at 16k and 70k (`STEP_TIMING`, `LLAMA_DECODE_TIMING`): find the
  0.4-0.7% (suspect: upstream batch API in server/speculative).
- Done when: pooled within 0.3% of integrate16 and depth within noise; tag `r9700-integrate17` = rb + fix;
  push fork branches.
- Kill: if no host term explains it in 0.5 day, accept rb as base anyway (gates pass) and note the cost.

### W2. Qwen3.8-27B Q4_K_M: decide by quality (~1.5 h GPU)
- Run `q4e.sh` phases pool, prompt, vram, gates (depth already done: decode +16% / +6.5%, prefill
  -19% / -6%, row Q4E1).
- Done when: pooled t/s, 32.5k prompt, VRAM peak, PPL, KLD and acceptance are in results.tsv.
- Keep Q4_K_M as a serving candidate only if KLD at 70k <= ~3x Q6_K's and pooled acceptance drops
  < 0.02. Otherwise Q4 for the 27B is closed (the kernel work below still pays for the other models).

### W3. Q4_K / Q5_K decode kernels (largest shared lever, ~3-5 days)
- First (15 min GPU): W0 bandwidth report on the 27B Q4_K_M and Ornith Q4_K_M. Our tuned Q6_K MMVQ reaches
  most of the bandwidth floor; the Q4_K/Q5_K numbers say how much is left.
- Port the Q6_K decode path (MQ5 n=5 fast path, rows-per-workgroup, DRAM-bound layout) to Q4_K and Q5_K,
  behind `GGML_VK_NO_MQ4`/`GGML_VK_NO_MQ5K` switches, RDNA4-gated.
- Done when: Q4_K and Q5_K decode GEMVs reach within ~10% of the Q6_K path's bandwidth efficiency, with
  test-backend-ops MUL_MAT/MUL_MAT_VEC_FUSION green, and decode t/s up on every Q4_K_M/Q5 model.
- Kill: if the bandwidth report shows Q4_K/Q5_K already within 10% of Q6_K's efficiency, skip to W4.

### W4. MoE: MUL_MAT_ID for Qwen3.6-35B-A3B (~2-3 days)
- Baseline profile (W0); expect expert dispatch, gather and small per-expert GEMVs to dominate decode.
- Tune MUL_MAT_ID decode (n=1..5 tokens x 8 experts) for Q5_K/Q6_K/Q8_0; take upstream 94a0ae3e7 tiles for
  prefill (already in RB); MTP drafting on the MoE (nextn 1) through our host pipeline.
- Done when: decode t/s and prefill t/s are measured vs upstream and the fork beats upstream on both,
  gates (PPL/KLD/acceptance) unchanged.

### W5. Gemma4-E4B (~2-3 days)
- Bring-up on RB with the LM Studio Q4_K_M + mmproj; confirm the fork loads it and matches upstream text.
- Profile (W0). Expected terms: 42 small layers (2560 wide) make it launch/host-bound at decode; the
  262k-vocab output head is Q6_K (our MMVQ applies); per-layer embedding lookups are GET_ROWS (check
  the host GET_ROWS path from HGR is safe there); attention is SWA 512 with head dim 256, plus 1 in 6 global
  layers at head dim 512 (FA head-size coverage: FA320 SIGFPE is a known hole, so check hsk 512 the same way).
- No MTP: compare speculative options: Gemma4-E2B as a draft model (same tokenizer), n-gram lookup, none.
  Keep whichever raises pooled t/s.
- Done when: fork >= upstream on decode and prefill for E4B, with a chosen draft policy and gates.

### W6. Tuning (runs alongside W3-W5, mostly scripted)
- **Kernel parameter tuning**: a sweep tool over test-backend-ops perf for the shapes each model actually
  runs (from W0 op tables): rows/WG, split-K, workgroup size, MMVQ n-fast-path, per quant. Results go into
  an arch-gated table, not into hard-coded constants.
- **Runtime config per model**: ubatch/batch, KV type (q8_0 vs q4_0 per K/V), `-fa`, draft n_max and
  p_min, draft KV types, context size vs VRAM headroom, mmproj lazy load. One sweep per model; the
  winner goes into that model's setup README as its serving config.
- Done when: every target model has a documented serving config backed by a sweep row.

### W7. GEN: keep general changes from hurting other models (~1 day, then per change)
- Every default-on fork change (fusions, graph_optimize, prealloc growth, MFL, VSUB, HGR) is screened on
  all targets via W0 (fork vs fork-with-switch-off). Any loss gets an arch/model gate. The Qwen3.8 Q6_K
  serving numbers must not move.
- The llvmpipe coopmat MUL_MAT failure is upstream's, not ours (queue GEN note).

### W8. Q4_K/Q5_K prefill GEMM port (conditional on workload answer, multi-day)
- Port the lean-dequant RDNA4 GEMM from Q6_K to Q4_K/Q5_K. Expected: Q4_K_M prefill back to Q6_K's level
  (+20% at 70k vs today's Q4 numbers), not beyond it: prefill is compute-bound.
- Runs only if long-prompt workloads matter.

### W9. Qwen4-27B readiness (ongoing, mostly cheap)
- Stay close to upstream: rebase cadence every 2-3 weeks (RB took 25 conflict hunks after 280 commits;
  smaller is cheaper). Day-0 support for a new arch lands upstream first.
- Gate fork kernels by what the tensors are (type, shape, head dim, arch features), never by model name, so a
  qwen35-like successor inherits the GDN/FA/MTP work automatically.
- W0 makes day-0 measurement a one-command job: profile, quality reference, acceptance.
- Day-0 checklist (in the new setup README when it ships): load in fork and upstream; text match; profile;
  find which of our paths engage (perf logger op names); quality reference; serving config sweep.
- Watch for features our kernels do not cover yet: new head dims (FA hsk coverage), new quant mixes
  (unsloth UD), MoE variants, larger vocab heads, multi-token heads > 1 (our pipe path is off for those).

## Also worth looking at (unscheduled, cheap to check)
- **Prompt/KV reuse** for agent sessions: cache hits avoid prefill entirely; check slot save/restore and
  `cache_prompt` behaviour with MTP on.
- **KV precision**: q8_0/q8_0 is fixed for the 27B; for the smaller models q4_0 V may free enough VRAM to
  keep more models resident.
- **Two models resident**: Gemma4-E4B (~5 GB) next to the 27B Q4_K_M (~17 GB) may fit 32 GB with
  reduced context; today only one model is allowed on the card (OOM rule). Measure before changing that rule.
- **Gaming coexistence**: GPU runs need the card idle; `harness/gpu_lock.sh` should refuse to start when
  another process holds the card (ollama, games), not only when another perf-lab job does.

## Order and GPU budget
W0, W1, W2 first (they are cheap and unblock everything), then W3 then W4/W5 in parallel worktrees (one
GPU: measurements serialize through the lock), W6 and W7 alongside, W8 on the workload answer, W9 ongoing.
Each item appends rows to its setup's results.tsv; the root keeps the queue.
